# NovaSight Product Roadmap Design

## 定位

NovaSight 的下一阶段目标不是继续堆功能，而是把现有工程整理成一个可售卖、可维护、可真机交付的 Jetson 视觉辅助工作台。

项目需要同时满足三个身份：

- 开发者视角：链路清晰、模块边界明确、日志能定位问题。
- 用户视角：启动后知道当前能不能采集、能不能推理、为什么失败。
- 商家视角：授权、模型交付、诊断、售后排障和版本迭代都能闭环。

## 当前判断

NovaSight 已经相比原始 `untitled` 具备更好的产品方向：

- 前后端已经有基本联动。
- 采集能力、运行状态、授权许可、模型目录扫描、ONNX/TensorRT 后端已经有雏形。
- 推理结果、运行统计、控制量输出已经开始进入统一运行链路。

但当前还不是完整产品，主要风险是：

- 真机闭环仍未被稳定证明。
- 推理失败、模型不匹配、采集异常等问题虽然开始展示，但还不够可诊断。
- UI 部分页面仍偏“配置堆叠”，没有完全按真实用户任务组织。
- 模型仓库、推理配置、预览绘制、控制量输出之间的关系还需要更强绑定。

## 产品路线选择

推荐路线：工程闭环优先，UI 产品化同步推进。

不采用“先做漂亮 UI”的路线，因为后端闭环未稳定时，漂亮界面会掩盖真实问题。不采用“先做插件生态”的路线，因为当前基础能力还没稳定，生态会放大维护成本。

本阶段的核心原则：

- 采集、推理、控制必须围绕真实数据。
- 前端显示的状态必须来自后端真实状态。
- 推理失败必须有明确原因，不能只在前端显示一个模糊错误。
- 预览流可以限帧，但不能拖慢采集和推理主线。
- 不继续写小覆盖面测试脚本；最后阶段再整理有价值的 pytest 覆盖。

## 阶段 1：真机闭环稳定

目标：Jetson 上稳定完成：

```text
采集流 -> ROI Frame -> 推理 -> 目标输出 -> 控制量计算 -> 前端展示
```

### 采集链路

正式主线应以 Jetson GStreamer 为核心：

```text
/dev/video0
  -> v4l2src
  -> MJPG/NV12/YUYV
  -> nvv4l2decoder/nvvidconv
  -> NVMM/NV12 ROI
  -> 推理消费者 + 预览消费者
```

要求：

- 采集输入源必须可选，不能前端自动替用户决定。
- 格式按类型分组展示，不使用长表格堆枚举。
- 每个格式内部按 FPS 优先排序，再考虑分辨率。
- ROI 输出尺寸必须可以在采集设置中修改。
- 预览 FPS 只能影响浏览器推流，不能影响主线采集和推理。

### 推理链路

模型来源改为服务端扫描 `models/` 目录：

```text
models/
  model-a.onnx
  model-b.engine
  classes.txt
  metadata.yaml
```

要求：

- `.onnx` 自动走 ONNXRuntime。
- `.engine` 自动走 TensorRT。
- 用户不手动选择推理后端。
- 加载失败必须反馈到前端，并写入后端日志。
- 推理配置必须与当前模型建立绑定关系，包括输入尺寸、类别名、置信度、NMS 阈值。

### 推理结果展示

前端必须明确展示：

- 当前是否正在推理。
- 当前模型名称和后端。
- 输入尺寸和像素格式。
- raw detection 数量。
- mapped detection 数量。
- 最近一次失败原因。
- 目标框、类别名、置信度。

目标框必须绘制在真实 ROI 预览区域，不能使用写死的蓝色框或假 FOV。

### 控制量输出

推理目标必须进入控制量计算：

```text
Detection -> Target Selection -> PID/控制策略 -> MoveCommand -> 输出端
```

第一阶段输出端保留：

- dry-run 静默对象。
- 命令行日志对象。

后续再接入 kmNet 或硬件盒子。

PID 默认参数：

- `kp_x`
- `kp_y`
- `ki`
- `kd`
- `max_dx`
- `max_dy`

其中 `kp_x/kp_y` 分轴，`ki/kd` 共用，最终控制量必须被 `max_dx/max_dy` 限制。

## 阶段 2：产品工作台

目标：让用户面对的是一个专业工具，而不是开发调试页面。

### 性能指挥台

只展示运行数据，不做复杂配置。

内容：

- 采集 FPS。
- 推理 FPS。
- 预览 FPS。
- 最近窗口内丢帧。
- 最近窗口内跳帧。
- E2E 延迟。
- 当前目标数量。
- 控制输出状态。
- 消费者开关状态。

统计方式：

- UI 每 250ms 刷新。
- FPS 使用最近 1 秒滑动窗口。
- 丢帧和跳帧显示窗口值，不显示无限累计值作为主指标。

### 基础设置

基础设置是统一配置中心，不再把采集、推理、算法拆成松散页面。

建议结构：

```text
基础设置
  ├── 采集设置
  ├── 推理设置
  └── 控制设置
```

交互风格采用 SaaS 设置页：

- 左侧为设置分组。
- 右侧为当前分组表单。
- 表单使用分段控件、选择器、滑条、数字输入、开关。
- 高级内容默认折叠。
- 修改后显示“未保存/已同步/同步失败”。
- 后端配置与前端配置键必须保持一致。

### 模型仓库

模型仓库面向消费者，不面向开发者。

用户应该看到：

- 模型名称。
- 文件类型：ONNX / TensorRT Engine。
- 是否可加载。
- 输入尺寸。
- 类别数量。
- 推荐置信度。
- 是否已绑定当前推理配置。
- 最近一次推理状态。

模型仓库必须能直接驱动推理配置：

- 选择模型后，推理配置自动切到该模型。
- 模型加载失败时，推理配置显示不可用原因。
- 模型元数据缺失时，提示用户补齐类别名或输入尺寸。

### 授权许可

授权页需要有商业产品感。

展示：

- 当前权益等级。
- 当前时间。
- 到期时间。
- 剩余天数。
- 设备绑定状态。
- 可用功能。
- 测试卡密和正式卡密的状态差异。

不展示创建时间。创建时间属于服务端审计信息，普通用户更关心“现在是否有效”和“什么时候到期”。

## 阶段 3：商业化交付

目标：让 NovaSight 可以售卖、远程排障、版本迭代。

### 一键诊断

提供诊断报告：

- Jetson 型号。
- 系统版本。
- Python 版本。
- GStreamer 插件。
- TensorRT 可用性。
- CUDA 可用性。
- `/dev/video*` 能力。
- 当前模型可加载性。
- 授权状态。
- 后端端口。
- 前端 API base URL。

报告可导出，方便售后远程判断问题。

### 日志分层

用户界面显示中文错误：

- 采集设备被占用。
- 模型加载失败。
- TensorRT 不可用。
- 类别名缺失。
- 授权过期。
- 控制输出未启用。

后端日志保留完整技术原因：

- 异常堆栈。
- GStreamer pipeline。
- TensorRT binding 信息。
- 模型输入输出 shape。
- 请求 URL 和状态码。

### 模型交付规范

每个可交付模型建议包含：

```text
model-name/
  model.onnx 或 model.engine
  classes.txt
  metadata.yaml
```

`metadata.yaml` 至少包含：

- display_name
- backend
- input_width
- input_height
- class_names
- confidence_threshold
- nms_threshold
- recommended_capture_profile

## 验收标准

阶段 1 完成时：

- Jetson 上能选择真实采集源。
- 能选择 ROI 输出尺寸。
- 能加载 ONNX 或 Engine。
- 前端能看到推理成功或失败原因。
- 有目标时能在预览中绘制目标框。
- 控制量能被 dry-run 或命令行输出。

阶段 2 完成时：

- 性能指挥台只展示真实数据。
- 基础设置能同步修改采集、推理、控制配置。
- 模型仓库与推理配置建立真实联动。
- 授权页能表达商业权益和到期信息。

阶段 3 完成时：

- 用户可以导出诊断报告。
- 商家可以根据报告快速定位环境问题。
- 模型交付有标准目录和元数据。
- 项目具备售卖和维护的基本条件。

## 下一步执行顺序

1. 修正和验证 TensorRT/ONNX 推理闭环。
2. 将推理结果绘制到真实 ROI 预览。
3. 强化模型仓库与推理配置绑定。
4. 重构基础设置页为 SaaS 风格配置中心。
5. 增加 Jetson 一键诊断与日志导出。
