# NovaSight Code Audit

Generated for `deepseek_project.md` Phase 0.2.

## Scope

This audit classifies the current repository surface and records code that must be removed,
replaced, or constrained before the later NVMM/DeepStream phases can be considered complete.
Line references are from the current working tree at the time of this audit.

## Module Map

### Capture

- `novasight/capture/device_probe.py` probes V4L2 devices into structured capabilities.
- `novasight/capture/pipeline_planner.py` creates initial `PipelinePlan` objects and cached
  GStreamer validation strings.
- `novasight/capture/caps.py`, `profile.py`, `state.py` expose the older capability/profile API.
- `novasight/capture/pipeline.py` builds legacy candidate GStreamer strings from `CaptureProfile`.
- `novasight/capture/source.py` opens OpenCV and GStreamer frame sources and converts appsink
  samples into `CapturedFrame` objects.
- `novasight/capture/session.py`, `service.py`, `preview.py` own capture lifecycle and preview.
- `scripts/probe_full.py` writes Phase 0 hardware capability and baseline JSON files.

### Inference

- `novasight/inference/onnxruntime_engine.py` is the ONNXRuntime fallback path.
- `novasight/inference/tensorrt.py` owns TensorRT execution, host fallback, and device tensor
  binding.
- `novasight/inference/preprocess.py`, `input.py`, `postprocess/yolo.py` handle tensor input
  preparation and YOLO decoding.
- `novasight/deepstream/pipeline_builder.py` builds the current DeepStream pipeline string.
- `novasight/deepstream/backend.py` runs DeepStream and extracts tensor metadata through `pyds`.
- `novasight/model_registry/*` scans model artifacts, manifests, fingerprints, and nvinfer
  config files.

### Control and Hardware

- `novasight/control/angular.py` maps image error to angular PD output.
- `novasight/control/strategy.py` converts tracks/detections into `ControlIntent`.
- `novasight/control/output.py` clamps/rejects control output.
- `novasight/control/scheduler.py` holds the latest command, applies TTL, splits large moves, and
  records scheduler metadata.
- `novasight/hardware/kmbox_net.py`, `makcu.py`, `factory.py` implement hardware output adapters.
- `novasight/runtime/service.py`, `tracker.py`, `aim.py`, `pipeline.py`, `replay.py` join capture,
  inference, target state, latency compensation, scheduling, and replay.

### UI and API

- `novasight/api/*` exposes health, device, capture, model, runtime, and executor endpoints.
- `web/src/features/*`, `web/src/components/*`, `web/src/app/*`, `web/src/api.ts`, and
  `web/src/styles.css` implement the browser console.

## Findings and Remediation Targets

### CAP-001: Legacy capture builders still hard-code GStreamer candidates

- Evidence: `novasight/capture/pipeline.py:28-87`, `90-202`, and `205-320` construct MJPG/NV12/YUYV
  pipelines directly from `CaptureProfile`, including fixed `io-mode=2`, `io-mode=4`, `YUY2`,
  `BGRx`, and `video/x-raw(memory:NVMM)` variants.
- Risk: this bypasses the new `DeviceProbe`/`PipelinePlanner` decision boundary and can keep
  unsupported formats alive after Phase 1.
- Replace with: make `CaptureService` and source factories consume `PipelinePlan` generated by
  `PipelinePlanner`; keep these functions only as compatibility shims or delete them after the
  planner path is the sole production capture path.

### CAP-002: OpenCV capture path returns CPU BGR frames

- Evidence: `novasight/capture/source.py:199-205` opens `cv2.VideoCapture` through V4L2 or
  GStreamer; `source.py:219-241` returns CPU `image` data with no source timestamp.
- Risk: OpenCV capture cannot satisfy the planned NVMM zero-copy data plane and should not be
  used in the production Jetson path.
- Replace with: route production capture through GStreamer/PipelinePlan and `GstResourceFrameSource`
  or the planned `CaptureLoop`; keep OpenCV only for explicit development fallback if clearly
  marked as CPU mode.

### CAP-003: Appsink CPU conversion maps buffers into host memory

- Evidence: `novasight/capture/source.py:321-355` calls `_sample_to_bgr`; `source.py:625-646`
  maps `Gst.Buffer`, uses `np.frombuffer`, reshapes, and copies BGR/BGRx/NV12 data into host
  arrays.
- Risk: violates Phase 2's "no Gst.Buffer copy to CPU side" requirement.
- Replace with: production appsink path should store the original `Gst.Sample`/`Gst.Buffer` in a
  single-slot latest buffer and pass `FrameResource` metadata downstream; CPU conversion should be
  restricted to preview/debug fallback.

### CAP-004: Resource appsink is closer but still not a standalone CaptureLoop

- Evidence: `novasight/capture/source.py:358-398` preserves GPU-accessible resources without
  image extraction, and `source.py:451-468` reads PTS/DTS into metadata.
- Gap: Phase 1.3 still requires an explicit `LatestFrameBuffer` and `CaptureLoop` skeleton that
  writes `(GstBuffer, FrameContext)` from an appsink callback.
- Implement next: `novasight/capture/capture_loop.py` with a single-slot buffer, non-copying
  `put/get`, `do-timestamp=true` usage, and a reserved frame metadata interface.

### INF-001: ONNXRuntime remains a direct inference path

- Evidence: `novasight/inference/onnxruntime_engine.py:48-56` imports ONNXRuntime, `104-127` loads
  ONNX models, and `129-196` runs `InferenceSession.run`.
- Risk: acceptable only as fallback/development; Phase 3 production inference should be
  DeepStream/TensorRT integrated into the capture pipeline.
- Replace with: mark ONNXRuntime as non-production fallback in runtime selection and ensure
  DeepStream is the required Jetson production backend once Phase 3 is complete.

### INF-002: TensorRT host path still copies H2D and D2H

- Evidence: `novasight/inference/tensorrt.py:423-443` prepares host input and copies
  HostToDevice; `448-462` copies DeviceToHost before decode.
- Risk: violates the zero-copy objective when this path is selected.
- Replace with: production TensorRT path should enter through `_execute_device_tensor`; use host
  path only as explicit fallback and expose status evidence when it is used.

### INF-003: TensorRT device path still copies output back to CPU for decode

- Evidence: `novasight/inference/tensorrt.py:540-575` executes a device-bound input but still
  enqueues DeviceToHost for selected output; DeepStream tensor extraction similarly copies at
  `novasight/deepstream/backend.py:681-695`.
- Risk: postprocess remains CPU-bound unless models emit final boxes or GPU-side parsing is used.
- Replace with: prefer models with EfficientNMS/final detection outputs in DeepStream, or move YOLO
  custom parsing/NMS to a DeepStream custom parser/CUDA path.

### DS-001: DeepStream pipeline builder is MJPEG-only

- Evidence: `novasight/deepstream/pipeline_builder.py:19-21` defaults `pixel_format="MJPG"` and
  `io_mode=2`; `32-80` always emits `image/jpeg`, `jpegparse`, and `nvv4l2decoder`; `84-90`
  rejects non-MJPG formats.
- Risk: conflicts with Phase 1 planner preference for NV12 when available.
- Replace with: build DeepStream source/decode segments from `PipelinePlan.capture_format` and
  `decode_backend`; allow NV12/no-decode and MJPG/decode candidates selected by the planner.

### DS-002: DeepStream runtime parses pipeline strings directly

- Evidence: `novasight/deepstream/backend.py:146-180` calls `Gst.parse_launch` on
  `self.pipeline_description`.
- Risk: pipeline construction and validation remain split between string builders instead of a
  typed plan, making cache validation and format fallback harder to prove.
- Replace with: make `DeepStreamDetectionBackend` accept the typed plan or a DeepStream pipeline
  object produced from it, with validation evidence captured before start.

### CTRL-001: Control path has timestamps, prediction, and scheduling metadata

- Evidence: `novasight/contracts.py:145-171` requires positive `capture_ts_ns`,
  `inference_start_ts_ns`, and `inference_end_ts_ns`; `novasight/control/scheduler.py:72-181`
  emits command IDs, source frame/track IDs, created/expiry timestamps, TTL, and cancellation
  metadata.
- Status: this satisfies the Phase 0.2 audit question that control output includes timestamps,
  prediction-aware TTL, and scheduling metadata.
- Keep/extend: when Phase 5 starts, verify that every control output can be traced back to the
  capture timestamp and predicted state used for latency compensation.

## Phase 0.2 Acceptance Summary

- File inventory with capture/inference/control/UI classification: complete in this document.
- Hard-coded capture formats and GStreamer strings: identified in CAP-001, CAP-002, CAP-003,
  DS-001, and DS-002.
- GPU-to-CPU copies: identified in CAP-003, INF-002, and INF-003.
- Direct ONNXRuntime/TensorRT inference paths: identified in INF-001, INF-002, and INF-003.
- Control timestamp/prediction/scheduling status: recorded in CTRL-001.

## Suggested Next Phase Order

1. Implement Phase 1.3 `LatestFrameBuffer`/`CaptureLoop` using `PipelinePlan`, without CPU image
   extraction.
2. Replace production capture selection with `PipelinePlanner` and demote `capture/pipeline.py`
   builders to compatibility fallback.
3. Add Phase 2 `gst_validator.py` to prove NVMM buffer memory before any inference integration.
